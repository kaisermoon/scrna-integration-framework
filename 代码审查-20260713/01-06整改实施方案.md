# scRNA-seq 整合分析框架 01-06 整改实施方案

## 1. 文档定位

本方案将 [[全仓代码审查总报告]] 及其专项报告中的 01-06 问题，连同 2026-07-13 PI 逐项拍板的科研与产品决策，转化为可直接实施、逐 PR 验收的整改路线。

本轮目标不是在现有代码上零散修补，而是建立一条满足以下条件的正式科研基线：

1. 数据尺度和统计输入语义明确，不依赖变量名猜测。
2. 所有必需步骤失败时立即阻断，不生成伪成功 checkpoint。
3. Notebook 在 fresh kernel 下可完整复现，公开参数真实生效。
4. 研究者能够看懂、调参、比较和选择，不需要维护底层 Python 工程。
5. 自动方法只提供证据和建议，最终科研选择由研究者或 PI 明确完成。

当前 `main` 继续维持 **BLOCK**。只有完成本方案规定的实现、测试和真实数据验收后，才可重新评估是否解除。

## 2. 本轮范围

### 2.1 纳入范围

- 01：各来源数据接入、counts 提取、QC、SoupX、doublet、高质量细胞输出。
- 02：跨来源合并、字段与特征对齐、尺度契约检查。
- 03：统一归一化、HVG 和预处理产物。
- 04：嵌入与批次整合方法运行、比较及研究者选择。
- 05：多分辨率聚类、充分比较及研究者选择。
- 06、06b、06c 中属于细胞注释、版本回流、PI 确认和正式产物提升的部分。
- 支撑上述阶段的 runner、CI、R 调用、状态机、run manifest、checkpoint 和 Notebook UX。

### 2.2 明确暂缓

以下模块不属于本轮 01-06 解锁条件，后续进入各自专项审查与整改：

- GRN。
- CellChat。
- trajectory-DE 及相关 pseudotime 正式产物。
- D02 pseudobulk DEG，包括 donor 统计单位、逐 cell type 分析、跨数据集混杂和 R 矩阵降维问题。

SoupX 校正结果在 DEG 中的具体使用方式随 D02 专项一并解决。本轮只建立独立数据分支和清晰契约，不提前改写 D02。

## 3. 已批准的核心决策

### 3.1 Raw counts 准入

- raw counts 是进入正式整合分析的准入条件。
- normalized-only 数据只能进入探索性分析，且不得伪造 counts。
- 当前 manifest 实际使用的四个来源均已找到真实 counts：
  - Nowicki：`raw.X` 为与当前对象同形、基因顺序一致的非负整数 counts；`X` 为 logcounts。
  - Kim：`X` 为真实整数 counts。
  - Nancang：10x/旧链及已有 counts layer 可取得真实 counts。
  - Yue：29 个输入文件存在真实 counts。
- Nowicki 完整原文件当前不在本机；现阶段结论针对 manifest 实际使用的子集文件，恢复完整文件后仍需复核。

### 3.2 01-03 表达矩阵契约

- `layers["counts"]` 是进入框架后的唯一原始 counts 权威位置。
- `.raw` 只作为输入提取来源或历史快照，不作为下游计算时的 fallback。
- 01、02 的 `X` 是 counts 工作矩阵。
- 03 及以后 `X` 是从 `layers["counts"]` 统一生成的 normalized/log1p 表达矩阵。
- `uns["expression_contract"]` 必须记录 `X` 尺度、counts 来源、验证状态、处理历史和当前分析矩阵选择。
- 禁止使用全局 `preprocessing_done`、变量是否存在或整数外观猜测矩阵语义。
- 禁止从 normalized `X` 复制、取整或改名生成 counts。

### 3.3 SoupX 独立分支

- 仅对同时具备完整 raw droplets 和 filtered cells 的来源启用，目前为 Nancang。
- `tod` 保留完整 droplet barcodes，`toc` 保留 filtered cell barcodes，只对齐基因，不能把 raw droplets 裁成 filtered cells。
- `layers["counts"]` 永久保留原始 filtered counts。
- SoupX 校正结果独立写入 `layers["counts_soupx"]`，记录参数、污染率、数值类型和状态。
- 启用 SoupX 后失败必须阻断该样本，不得把原 counts 冒充 corrected counts。
- PI 或研究者可以显式关闭 SoupX，使用未校正 counts 继续；这属于明确选择，不是自动 fallback。
- 校正后必须重新计算 QC，再进行过滤和 doublet 检测。
- `counts_soupx` 不进入 scVI/scANVI。
- `counts_soupx` 只供明确声明兼容的 QC、doublet、marker、可视化或 DEG 分支使用。
- 跨来源正式 DEG 不得无说明地混合“仅 Nancang 校正、其他来源未校正”的矩阵；主分析统一使用 raw counts，SoupX 结果留作后续专项敏感性或单来源分析。

### 3.4 Doublet 政策

- 按 sample 独立检测，不使用跨来源统一阈值。
- Nancang 在 SoupX 校正并重算 QC 后检测；其他来源使用各自验证后的 counts。
- 01 保留完整对象和审计信息，至少包括 score、prediction、threshold、include、方法和版本。
- 边界细胞只标记，不自动排除。
- 高置信 doublet 默认排除。
- 正式输出给 02 的是完成 QC 且已排除高置信 doublet 的高质量细胞子集。
- doublet 比例或阈值明显异常的样本进入 `NEEDS_REVIEW`，不得静默放行。
- 本轮不要求额外 doublet 敏感性分析。

### 3.5 scVI/scANVI 输入

- 默认只读取原始 `layers["counts"]`。
- 训练前全量或分块验证 shape、var 顺序、有限性、非负性、近整数性和文库大小。
- 04 不允许从 `.raw` 临时补救，也不允许复用已经判定非法的 counts layer。
- 研究者选择运行 scVI/scANVI 后，输入非法或方法失败必须显式失败，不得静默切换 Harmony、PCA 或其他方法。
- `layers["counts_soupx"]` 暂不作为 scVI/scANVI 默认或正式输入。

### 3.6 Notebook 执行纪律

- 01-06 必须通过 fresh-kernel 最小数据 `Run All`。
- 禁止使用 `dir()`、旧 kernel 变量或残留结果决定执行分支。
- 公开 `PARAMS` 必须真实传入方法，并在输出中打印和记录 effective parameters。
- 每个关键参数必须有参数消费测试。
- 04、05 的 `_m`/`m` 错误和 06b 版本变量先使用后定义必须立即修复，但这些只是止血，不构成全部整改。
- 06b 等巨型 cell 必须按输入检查、参数、执行、QC、选择和保存拆分。
- 必需步骤失败不得写正式 checkpoint。

### 3.7 版本与 PI-final 闸门

- 拆分并独立记录：
  - `UPSTREAM_LABEL_VERSION`
  - `ANNOTATION_OUTPUT_VERSION`
  - `SUBSET_OUTPUT_VERSION`
  - `MAIN_OUTPUT_VERSION`
- 路径、列名和元数据必须从同一份解析后的版本配置生成。
- LLM、marker 规则和 `Cluster_N` 只能写 suggested/draft，不得直接写 final。
- 未确认时只能保存 draft h5ad 和状态报告。
- final 必须满足：
  - `PI_CONFIRMED=True`；
  - 全 cluster 覆盖；
  - 无 unresolved；
  - 确认文件版本与输入一致。
- 确认记录必须包含逐 cluster 决定、确认文件 hash、时间和 annotation version。
- 批量接受建议也必须是显式操作，并形成逐 cluster 审计记录。
- `Cluster_N` 只能表示 unresolved 占位，不能作为有效细胞类型标签。
- 06c subset 注释和回流主对象执行相同门禁。

### 3.8 外部 LLM 边界

- 项目上游保证输入数据已经脱敏，框架信任这一治理边界。
- 不增加逐次二次脱敏、k 匿名检查或 PI 外发审批。
- 允许向配置的外部 LLM 发送现有脱敏实际值或聚合分析信息。
- 修复同 provider 多 group 相互覆盖的问题，路由以唯一 `LLM_GROUP` 为键。
- 每次调用记录实际 group、provider、model、endpoint 和参数，用于复现。
- 外部服务留存及未发表分析信息外发作为已接受残余风险。
- 环境 pin、适配代码和声明版本必须一致；远端契约测试不得使用真实数据。

## 4. Stage 状态机与产物提升

### 4.1 方法状态

每个方法必须记录以下状态之一：

- `success`
- `skipped_by_user`
- `unavailable`
- `failed`

不得把 `unavailable`、`skipped` 或 fallback 后继续运行记为 `success`。

### 4.2 Stage 状态

| 状态 | 含义 | 是否可生成正式 checkpoint |
|---|---|---|
| `FAILED` | required 步骤或 hard postcondition 失败 | 否 |
| `NEEDS_REVIEW` | 计算完成，但等待 embedding、resolution 或 annotation 决策 | 否，仅 draft |
| `SUCCESS_WITH_WARNINGS` | 必需条件满足，但有 optional 失败或显著 warning | PI/研究者接受 warning 后才可提升 |
| `SUCCESS` | required 和 hard postconditions 全部通过 | 是 |

所有运行先写临时或 draft 目录，通过 hard postconditions 后再原子提升。失败运行不得留下可被下游自动发现的正式文件名。

### 4.3 Required 样本纪律

- manifest 中声明为 required 的样本失败后，不能在运行中自动删除后继续。
- 若研究者决定排除该样本，必须修改 manifest、说明原因并生成新版本。
- optional 样本也必须在运行开始前明确声明，不能根据运行结果事后改写身份。

## 5. 01-06 最低成功条件

### 5.1 Stage 01：接入、QC 与高质量细胞

必须产物：

- 每来源经过验证的 01 h5ad。
- 完整对象审计产物。
- 过滤和 doublet 排除后的高质量正式对象。
- 每 sample 的输入、counts、QC、SoupX、doublet 和过滤状态表。

Hard postconditions：

- `layers["counts"]` 存在，且与 obs/var 完整对齐。
- counts 全部有限、非负、近整数。
- 必需 obs 字段完整且来源可追溯。
- 过滤前后细胞数和 QC delta 按 sample 正确记录。
- 启用 SoupX 时 `tod/toc` 语义正确，校正成功并重算 QC。
- doublet 检测完成，高置信 doublet 未进入正式输出。
- required 样本全部成功。

### 5.2 Stage 02：跨来源合并

必须产物：

- `02_merged_<version>.h5ad`。
- 逐来源输入 manifest 和 schema/feature 对齐报告。

Hard postconditions：

- 所有 required 01 checkpoint 均为可提升状态。
- cell ID 全局唯一。
- source、sample、donor、disease 等关键字段可追溯。
- `layers["counts"]` 在所有来源中语义一致、形状正确。
- 不存在 raw 与 normalized 混合 concat。
- 不使用任一来源状态替代全体来源检查。

### 5.3 Stage 03：统一预处理

必须产物：

- 保留原 counts 的统一 normalized/log1p 对象。
- HVG 标记、参数和诊断。

Hard postconditions：

- `layers["counts"]` 前后摘要或 hash 不变。
- `X` 明确由 counts 按统一规则生成且全部有限。
- HVG 非空，参数、批次键和选择结果可追溯。
- 不从 `X` 伪造 counts。

### 5.4 Stage 04：嵌入与整合

研究者在 Notebook 中勾选本次运行的方法，不设置固定方法 profile。

交互要求：

- 每种方法提供运行勾选项。
- 同屏说明前置条件、输入、GPU/时间成本、适用场景和主要风险。
- 勾选结果进入 run manifest。
- 前置条件不满足时禁用并显示原因。
- 每个被选择的方法独立记录状态。
- 只比较实际运行的方法。

Hard postconditions：

- 至少一个被选择的方法成功并产生有限、维度正确的 embedding。
- 所选方法输入满足各自契约。
- 比较表非空且与实际成功方法一致。
- 研究者显式填写 `selected_embedding` 后，stage 才能从 `NEEDS_REVIEW` 提升。
- 部分方法失败时进入 `SUCCESS_WITH_WARNINGS`，由研究者决定是否接受。

### 5.5 Stage 05：多分辨率聚类

研究者选择候选 resolutions，系统负责充分展示，不自动排名或淘汰。

每个 resolution 必须展示：

- cluster 数量和最小 cluster 大小。
- sample、donor、disease 和 dataset 构成。
- 是否由单一 batch 或来源主导。
- marker 数量、特异性和谱系合理性。
- 是否出现缺乏 marker 支持的过度碎片化。
- 低质量细胞或 uncertain doublet 富集。
- 不同 seed 或邻居参数下的稳定性。
- 并排 UMAP 和核心指标表。

Hard postconditions：

- 所有被选择的候选 resolution 均产生完整聚类列。
- 每列全细胞覆盖，且至少有两个 cluster。
- 指标、图表与对应聚类列严格一致。
- 系统只显示风险提示，不自动写最终 key。
- 研究者显式填写 `selected_cluster_key`，可附选择理由，随后才可提升。

### 5.6 Stage 06：证据、建议与最终注释

必须产物：

- 每 cluster 的非 LLM 证据包。
- 各方法 suggested 标签。
- 全 cluster PI 决策文件。
- 确认后生成的 final 标签和正式 checkpoint。

Hard postconditions：

- 至少一个非 LLM 证据源成功。
- suggested、draft、final 列严格分离。
- 全 cluster 覆盖，无 unresolved。
- PI 确认文件 hash、时间和版本正确记录。
- subset 及主对象回流版本完全一致。
- 未确认或部分确认时只能写 draft。

## 6. Guided Notebook 产品设计

### 6.1 目标用户

面向懂生物医学研究与单细胞分析判断、但不希望维护底层 Python 工程的研究者。Notebook 是主要科研界面，`src` 只承担纯技术管道。

### 6.2 统一页面结构

每个 01-06 Notebook 使用相同结构：

1. 本阶段的生物学问题、输入、输出、适用边界和不能证明什么。
2. 唯一可编辑 `PARAMS` 区域。
3. bootstrap/import。
4. 输入 preflight 和 effective parameters。
5. 按“准备、执行、中间 QC”拆分的方法块。
6. 候选结果同屏比较。
7. 独立的研究者或 PI 选择 cell。
8. hard postconditions、方法状态和 stage 状态。
9. draft 或 promoted checkpoint 保存。

### 6.3 参数说明

参数按以下类别组织：

- 数据与版本。
- 科学参数。
- 计算参数。
- 输出与运行标识。

每个科学参数说明：

- 生物学或统计含义。
- 默认值和来源。
- 何时应调整。
- 调高或调低的主要后果。
- 对下游结论的风险。

不使用只解释 Python 语法的低价值注释。

### 6.4 Cell 边界

- 每个 cell 单一职责，通常控制在 20-60 行。
- 输入检查、参数、执行、QC、决策和保存不得混在同一巨型 cell。
- 会改变科研结论的阈值、算法选择、映射、冲突处理和诊断必须在 Notebook 中可见。
- `src` 仅保留 bootstrap、环境与平台检测、文件格式读取、RDS/跨语言桥接、LLM transport 等 plumbing。
- 断点恢复只能读取已验证 checkpoint 和 manifest，不读取 kernel 残留变量。

## 7. Run 管理与保留

每次调参生成独立 `RUN_ID`，不得覆盖既有 run。

每个 run 长期保留以下轻量证据：

- effective parameters。
- 输入文件 hash。
- Git、包、R 环境和随机种子。
- 方法状态和 stage 状态。
- QC 与比较指标。
- 图表。
- 研究者选择及理由。
- warning、错误摘要和产物清单。

大型 h5ad 分为：

- `promoted`：正式结果，保留。
- `pinned`：研究者指定的候选，保留。
- `superseded/failed`：不自动删除，进入 run 管理清单。

研究者只能通过 run 管理表显式勾选清理大型产物。清理后仍保留该 run 的 manifest、参数、指标和图表。失败 run 不生成正式 checkpoint，但保留诊断记录。临时目录与正式产物目录必须隔离。

## 8. PR 实施路线

### PR 0：确定性止血与真实失败传播

目标：先消除已知必崩和测试假绿，建立后续整改可依赖的最低执行基础。

修改：

- 修复 04、05 `_m`/`m` NameError。
- 修复 06b 版本变量先使用后定义及重复定义。
- 移除 CI、R 和 notebook runner 中的 `|| true`、`--allow-errors` 和强制成功退出。
- 确保 core cell、R job、产物检查失败均返回非零。
- 增加静态 F821 和 fresh-kernel 最小执行门禁。

验收：

- 已知 NameError 有回归测试。
- 人为制造 Python/R/core cell 失败时 CI 必须失败。
- 缺少 required 产物时 runner 必须非零退出。

### PR 1：共享运行契约、状态机与 run manifest

目标：统一所有阶段的状态、版本、路径和产物提升规则。

修改：

- 实现方法四态和 stage 四态。
- 引入 `RUN_ID`、draft/promoted 目录和原子提升。
- 建立 run manifest、输入 hash、effective parameters、环境和产物清单。
- 建立 hard postcondition 执行与报告接口。
- 建立 validated checkpoint 恢复机制。
- 拆分各类版本字段，取消路径、列名和元数据中的散落硬编码。

验收：

- `FAILED/NEEDS_REVIEW` 无法写入正式路径。
- `SUCCESS_WITH_WARNINGS` 未确认前无法提升。
- 相同 `RUN_ID` 不得无提示覆盖。
- checkpoint 与 manifest 不匹配时拒绝恢复。

### PR 2：Stage 01 counts、SoupX、QC 与 doublet

目标：为四来源建立真实 counts 和高质量细胞输出。

修改：

- Nowicki 从 `raw.X` 提取 counts。
- Kim、Nancang、Yue 从已验证来源建立 `layers["counts"]`。
- 实现 counts 全量或分块验证及 `expression_contract`。
- 修复 SoupX `tod/toc`、失败语义和校正后 QC。
- 独立保存 `counts_soupx`。
- 按 sample 执行 doublet，记录完整审计字段。
- 输出完整审计对象和去 doublet 的高质量正式对象。
- 修复过滤前后 QC 表记录顺序。

验收：

- 使用 [[h5ad-counts盘点]] 中四来源做实际契约验证。
- SoupX 最小 fixture 同时包含 raw droplets、filtered cells 和 ambient gene。
- SoupX 任一步失败不得生成 corrected 产物或 01 正式 checkpoint。
- 高置信 doublet 不进入正式 01 输出。

### PR 3：Stage 02-03 尺度统一

目标：根除 raw/normalized 混合 concat 和伪 counts。

修改：

- 02 合并前逐来源验证 counts、schema、cell ID 和关键 obs。
