# 全仓代码审查：架构与复现性

审查范围：项目主树的架构、文档/ADR、notebook、src、tests、scripts、CI、依赖与环境复现证据。

## 审查结论

**Verdict：block。**

当前架构方向本身正确：notebook 是生物医学专家的主要工作界面，`src/` 已大体收敛为技术管道；多数 notebook 有 PARAMS、中文步骤说明、回跑指引、守卫和可视化。但当前 `main=5129737` 仍存在会让 04、05、06b 在干净执行时直接失败的未定义变量；版本化回跑也会出现文件名、obs 列与 `adata.uns` 元数据不一致。required CI 不能拦截这些问题。

在修复 Critical 项并补上 notebook 静态/轻量执行门禁前，不应把当前 main 作为可靠的全流程基线继续扩展。

## Findings

### [Critical] A1. 04/05 核心比较循环引用未定义的 `m`

- **类型**：【事实】；已用 `ruff check --no-cache --select F821` 独立复核。
- **位置**：`notebooks/04_embedded.ipynb:1364`（cell 35，第 98 行）；`notebooks/05_clustered.ipynb:571`（cell 18，第 64 行）。
- **问题**：两个 cell 都把指标写入 `_m`，随后生成显示字符串时却遍历 `m.items()`。`m` 在该执行路径中未定义。
- **为何重要**：04 的多嵌入横向比较、05 的多分辨率指标比较是项目核心科研决策界面；循环第一次运行即 `NameError`，比较表、报告和后续 checkpoint 均无法可靠产出。
- **修改建议**：在两个 notebook 内将 `m.items()` 改为 `_m.items()`；增加针对这两个 cell 的静态 lint 门禁，并做一次最小 AnnData 的轻量执行回归。测试必须走真实 cell 调用路径，不能只测抽出的 helper。

### [Critical] A2. 06b 在定义前引用 `OUTPUT_VERSION`

- **类型**：【事实】；已由 ruff F821 确认。
- **位置**：`notebooks/06b_per_cluster.ipynb:105-118`（cell 3）。
- **问题**：`UPSTREAM_PATH` 与 `LABEL_COL` 先用 `OUTPUT_VERSION` 构造，`OUTPUT_VERSION = "v1"` 在后面才定义，而且重复定义两次。
- **为何重要**：从干净 kernel 顺序运行时，PARAMS cell 自身立即 `NameError`；只有旧 kernel 残留同名变量时才可能“偶然通过”，这是典型 notebook 隐式状态污染。
- **修改建议**：把 `OUTPUT_VERSION` 放在该 cell 首部且只定义一次，再派生路径和列名；增加“从清空 kernel 顺序执行 PARAMS + setup”的轻量测试。

### [Critical] A3. 版本化回跑契约仍会产生错误文件/列/元数据

- **类型**：【事实】；影响程度包含【推断】：用户按文档 bump 输出文件后，会得到错误或误标记的溯源状态。
- **位置**：`notebooks/06_annotated.ipynb:78-91`；`notebooks/06c_subset.ipynb:118-143,265-275,887-923,1020-1032`；`notebooks/07_downstream/D03_cnv.ipynb:694-695`；`notebooks/07_downstream/D04_pseudotime.ipynb:141-151,1498-1499`；`notebooks/07_downstream/D09_abundance.ipynb:131-135,1354-1355`。
- **问题**：06 暴露 `OUTPUT_VERSION`，但 `OUTPUT_PATH` 和下游标签仍要求人工同步；06c 的筛选表达式与多处检查写死 `cell_type_final_v1`；多个下游 notebook 教用户只 bump `OUTPUT_PATH`，却把 `adata.uns["version"]` 写死为 `"v1"`。
- **为何重要**：版本化回跑是项目核心能力。当前设计会读取旧标签、写到意外文件，或让 `_v2.h5ad` 内部仍声明 `version=v1`，导致后续科研分析无法可靠追溯。
- **修改建议**：每个 notebook 在 PARAMS 顶部只保留一个 `OUTPUT_VERSION`；所有路径、obs 列、uns key 和提示文本由该值派生。06c 另设 `UPSTREAM_LABEL_VERSION` 与 `SUBSET_OUTPUT_VERSION`，避免把上游粗标签版本和本轮精细标签版本混为一体。不要把版本推导藏进 src，保持在 PARAMS 可见。

### [Important] B1. required lint 是非阻断占位，已知 F821 因此进入 main

- **类型**：【事实】。
- **位置**：`.github/workflows/lint.yml:22-26`；`_project.md:13-18`。
- **问题**：仓库把 `lint` 声明为 required check，但 workflow 使用 `ruff check . || true`，任何 lint 错误都返回成功。
- **为何重要**：A1/A2 都能被 ruff 直接发现，却仍存在于 main，证明当前 required check 只提供绿色标记，不提供保护力。
- **修改建议**：在独立 CI PR 中移除 `|| true`；至少启用 `ruff check src tests scripts notebooks --select F,E9`。由于 CI workflow 属保护配置，按项目规则须独立 PR、PI 显式审批。

### [Important] B2. Notebook smoke 未接入 CI，且脚本自身不能作为可靠门禁

- **类型**：【事实】。
- **位置**：`.github/workflows/test.yml:44-50`；`tests/test_smoke.py:1-11`；`scripts/smoke_run_notebooks.py:29-61,99-181,185-256`。
- **问题**：CI 只跑 pytest；所谓 `test_smoke.py` 仅验证包导入。真正的 notebook runner 使用 `--allow-errors`，即使得到 `PARTIAL/ERROR`，结尾也不 `sys.exit(1)`。注释称 core 失败时跳过 downstream，实际无条件继续；D01-D14 的 `output_check` 全为空，不验证 checkpoint 是否存在。
- **为何重要**：notebook 是主要交付物，现有 CI 绿无法证明 23-stage 的代码可顺序运行、上游/下游契约连通或结果文件真实生成。
- **修改建议**：分两层门禁：PR 必跑“静态 notebook lint + PARAMS/setup 轻量执行 + 最小 fixture 的 03/04/05 契约测试”；重型全流程保留定期/人工 runner。runner 遇任何 `PARTIAL/ERROR/MISSING/NO_OUTPUT` 或预期产物缺失时必须非零退出，并在 core 失败时停止 downstream。

### [Important] B3. 启动脚手架迁移不完整，技术样板仍占据多数 notebook 首屏

- **类型**：【事实】。
- **位置**：`src/scrna_integration/bootstrap.py:1-89`；示例命中 `notebooks/02_merged.ipynb:64-76`、`notebooks/03_normalized.ipynb:109-121`、`notebooks/04_embedded.ipynb:115-128`、`notebooks/06_annotated.ipynb:155-169`；已迁移示例 `notebooks/01_per_dataset/01_kim.ipynb:50-54`。
- **问题**：`bootstrap.init()` 已专门承载找根、BLAS、sys.path 技术管道，但除模板和 Kim 外，多数活跃 notebook 继续复制约 20 行相同样板。
- **为何重要**：这违反项目 `src/notebook` 边界，也让生物医学用户打开 notebook 后先阅读环境胶水而非科研流程；复制版本已出现漂移，削弱维护性。
- **修改建议**：所有活跃 notebook 的第一段统一为 `from scrna_integration.bootstrap import init; _root = init()`；数据加载、参数、分析和可视化仍留 notebook。迁移后加结构测试，禁止活跃 notebook 再出现手写向上找根和 BLAS 四变量块。

### [Important] B4. 巨型 cell 破坏逐步运行、调试和教学透明

- **类型**：【事实】；“难以调试”的影响为【推断】，基于 cell 粒度与职责数量。
- **位置**：`notebooks/06b_per_cluster.ipynb` cell 7（306 行）；`notebooks/07_downstream/D13_gene_modules.ipynb:839-1079`（cell 13，241 行）；`notebooks/07_downstream/D05_pseudotime_monocle3.ipynb:527-730`（cell 9，204 行）；`notebooks/07_downstream/D04_pseudotime.ipynb:1122-1318`（cell 20，197 行）；`notebooks/06_annotated.ipynb` cell 27（185 行）；`notebooks/06c_subset.ipynb` cell 15（184 行）。
- **问题**：单个 cell 同时承担数据准备、方法调用、结果解析、绘图、保存、异常处理，部分还内联生成数百行 R 脚本。
- **为何重要**：用户要求 notebook 可调参、逐步运行和定位错误。巨型 cell 的任何中间失败都迫使整段重跑，变量状态不透明，也难以让医学研究生只修改一个科研步骤。
- **修改建议**：按“输入检查 → 参数/科研选择 → 方法运行 → 结果诊断 → PI 判断 → 保存”拆为独立 cell。R 流程中，科研参数和关键方法语句必须在 notebook 可见；文件搬运、命令构造、日志和超时等纯技术胶水可复用现有 scripts，不能把科研判断整体压进 src。

### [Important] B5. 多个真正影响结果的科研参数未进入 PARAMS

- **类型**：【事实】。
- **位置**：`notebooks/07_downstream/D13_gene_modules.ipynb:890-935`（PCA=30、metacell k=25、max_shared=10、R²=0.8）；`notebooks/07_downstream/D04_pseudotime.ipynb:1174`、`D05_pseudotime_monocle3.ipynb:579`（partition/close_loop）；`notebooks/07_downstream/D12_cell_communication.ipynb:610`（CellChat min.cells=10）；`notebooks/06_annotated.ipynb:1424-1520`（DEG 数、top gene 数、temperature）。
- **问题**：这些阈值和方法选择位于执行 cell 或 R 字符串内部，不在顶部 PARAMS；部分已有相似可见参数却未真正传入底层调用。
- **为何重要**：这些值会改变 metacell 构建、网络拓扑、轨迹结构、通讯过滤和 LLM 判决稳定性，属于科研判断而非技术常量。隐藏会造成“看似可调，实际未生效”。
- **修改建议**：把所有结果敏感参数提升到对应 notebook 的 PARAMS，并在调用前打印实际值；在运行元数据中记录。对固定值说明依据、适用范围和何时调整。参数仍留 notebook，不下沉 src。

### [Important] B6. 路径与 OS 判断违反跨平台和公开仓纪律

- **类型**：【事实】。
- **位置**：`scripts/make_test_subset.py:48-53`；`scripts/env_parity.py:161`；`src/scrna_integration/platform.py:17-20`；项目规则 `AGENTS.md:67-75`。
- **问题**：tracked 的抽样脚本硬编码真实 `/Users/...` 数据路径；`env_parity.py` 在 `platform.py` 外调用 `os.uname()`；`platform.py` 文档还写入真实用户名路径。
- **为何重要**：换机即不能运行，且 public 仓暴露本地目录信息；也破坏“OS 判断单点收口”的可审计性。
- **修改建议**：抽样脚本用 CLI 参数或本地 gitignored 配置接收数据根；文档使用 `~`/`<用户目录>`；`env_parity.py` 调用 `platform.platform_tag()` 或标准 `platform` 模块并在规则中明确诊断脚本例外，避免静默例外。

### [Important] B7. CI 环境与生产环境不是同一可复现对象

- **类型**：【事实】；“CI 绿不能证明生产可运行”为【推断】，由安装路径差异直接推出。
- **位置**：`pyproject.toml:27-95`；`.github/workflows/test.yml:24-48`；`environment.yml:1-41`；`docs/env-snapshots/osx-arm64.json:2-9`；`docs/env-snapshots/linux-64.json:2-9`。
- **问题**：生产环境使用精确 pin 的 conda spec，CI 却用 `pyproject.toml` 的 `>=` 松约束；安装失败还 fallback 到仅 pytest。Mac 快照仍是 Python 3.11.14，而当前 spec/Linux 为 3.11.15。
- **为何重要**：CI 解析出的依赖组合可与真实分析环境不同；Mac 快照也不能证明当前 spec 已在 Mac 验证。
- **修改建议**：CI 至少增加一个基于 `environment.yml` 核心约束的环境一致性检查，或由脚本比较 pyproject 下界与生产 pin；安装项目失败必须硬失败。刷新 Mac 快照，并在 PR 中记录差异是否预期。

### [Important] B8. 文档/ADR/状态文件不再描述当前实现

- **类型**：【事实】。
- **位置**：`README.md:82-85,130-132`；`CONTEXT.md:7-16,53-59,107-109`；`SPEC.md:30-161,952-983,1315-1321`；`references/markers/README.md:29-44,138-153`；`_plan.md:32-60,107-129`；`docs/MAC-SYNC.md:45-55`。
- **问题**：文档仍称 planning、3 个公开函数、read_with_manifest/load_markers/scorers 存在、旧下游命名和旧 Mac 安装方式；实际 src 与 notebook 已重构。
- **为何重要**：生物医学用户会按文档复制不存在的 API，或误判当前阶段/环境；这直接破坏“清晰指引”最高需求。
- **修改建议**：建立当前真相源优先级：项目级 `AGENTS.md` + `_project.md` + 最新 ADR/优化方案；更新 README/CONTEXT/SPEC/marker README/MAC-SYNC/_plan。历史 ADR 保留但加 `superseded_by`，不要删除决策历史。

### [Important] B9. 项目记忆声称关键 bug 已修，但当前 main 仍包含它们

- **类型**：【事实】。
- **位置**：`_memory.md:21-31`；当前 `git log -1` 为 `5129737`；A1/A2 所列 notebook。
- **问题**：记忆记录称 04/05 `m.items()`、06 系列版本问题已修复合并，但当前 main 静态检查仍复现。最近历史也未显示记忆中提到的修复 merge 成为当前 HEAD 祖先。
- **为何重要**：状态文件是项目权威来源；若它与代码不一致，后续 agent 会基于错误前提跳过验证，形成“文档绿、代码红”。
- **修改建议**：状态更新必须以 `git merge-base --is-ancestor <fix_sha> main`、targeted lint/test 和 main ref 三者为证据；无法验证的记录标成“声称完成/待实地核验”，不能写“已闭环”。

### [Minor] C1. 下游文件名已改 D 前缀，但标题与输出仍沿用旧编号

- **类型**：【事实】。
- **位置**：例如 `notebooks/07_downstream/D01_deg.ipynb:1`、`D03_cnv.ipynb:1,114-115`、`D04_pseudotime.ipynb:1,141-142`、`D05_pseudotime_monocle3.ipynb:1,109-110`。
- **问题**：文件名是 D01-D14，但标题仍显示 07/08/10b，默认输出也沿用 `09_cnv_v1.h5ad`、`10_pseudotime_v1.h5ad` 等旧编号。
- **为何重要**：不影响计算，但会增加结果目录辨识成本，医学用户难以把 notebook、checkpoint 和文档清单对应起来。
- **修改建议**：统一标题、输出默认路径和 `adata.uns["stage"]` 为 D 编号；如需保持向后兼容，在迁移说明中列旧→新映射。

## 正向评价

- 【事实】`src/scrna_integration/` 当前只有 bootstrap、platform、LLM、基因 ID/基因组位置等技术管道，整体边界方向符合 PI 7/10 定稿。
- 【事实】大多数活跃 notebook 有集中 PARAMS、分步骤 markdown、中文 why 注释、包/数据守卫、内存断言与 checkpoint；01、03、04、05、06 的科研决策点总体可见。
- 【事实】06 的 PI 拍板区支持 CSV 覆盖 LLM 预填，降低非 CS 用户直接编辑 dict 的语法风险；最终标签仍由 PI 决定。
- 【事实】环境 spec 精确 pin，平台差异有 ADR 和异常登记；src 技术函数的 unit tests 覆盖较丰富，mock 大多位于 HTTP、文件系统、平台/第三方包等系统边界。
- 【事实】所有 tracked notebook 已清 execution count/output，数据和结果目录受 gitignore 约束，未发现大结果误入本次 tracked 清单。

## 建议修复顺序

1. **阻塞批**：A1 + A2 + A3，仅修 notebook 正确性与版本契约；目标是 clean-kernel 轻量执行通过。
2. **门禁批（独立保护配置 PR）**：B1 + B2，启用 notebook lint，修 smoke 非零退出与产物验收。
3. **生物医学友好性批**：B3 + B4 + B5，把技术样板收口、巨型 cell 拆小、科研参数提升到 PARAMS；不把科研逻辑压进 src。
4. **复现与治理批**：B6 + B7 + B8 + B9，清理路径、刷新快照、统一文档真相源与状态核验流程。
5. **命名清理**：C1，可与文档批合并但不要与核心算法修改混在同一 PR。

## 验收门槛

- `ruff check --no-cache --select F821 notebooks` 无真实未定义变量；对 `dir()` 守卫等误报用明确初始化替代，不用全局忽略。
- 04/05 用最小 AnnData 真跑比较 cell，产出非空比较表；06b 从 clean kernel 完成 PARAMS/setup。
- 将 06/06c/D 模块版本改为 v2 后，文件名、obs 列、uns key、`adata.uns["version"]` 全部一致且不覆盖 v1。
- required lint 在注入一个 F821 时必须红；smoke 出现任一错误或缺产物必须非零退出。
- 每个活跃 notebook 的首个可执行段只含 bootstrap + 必要导入；科研参数集中在 PARAMS，运行时打印实际值。
- 任何超过约 100 行的 cell 都需说明为何不能再拆；PI 决策前后的数据准备、方法执行、诊断和保存应分 cell。
- public tracked 文件不含真实用户绝对路径；Mac/Linux 快照与当前环境 spec 对齐或显式登记差异。
