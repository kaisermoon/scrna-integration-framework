# 技术管道与测试代码审查

## 审查结论

**Verdict：block。** 当前 Python 单元测试虽为绿色，但存在 4 个会直接损害结果可信度或造成假成功的 Critical 问题：SoupX 输入构造错误、SoupX 会把未校正矩阵伪装成校正结果、DESeq2 入口把矩阵降成向量、notebook 冒烟运行器无论失败与否均以退出码 0 结束。另有多处代码违反“生物医学专家需要调整的分析逻辑必须留在 notebook”的项目铁律。

本轮未修改生产代码。建议先处理 Critical，再做 notebook 透明化重构，最后收紧 CI；在此之前，“141 tests passed”不能作为 23-stage 管线科研有效性的验收依据。

## 做得正确的部分

- `src/scrna_integration/platform.py` 将设备与 Rscript 路径检测集中管理，方向符合跨平台目标，错误消息总体可诊断。
- `src/scrna_integration/llm_config.py` 对 HTTP 错误使用 `raise_for_status()`，且请求设置了 timeout，没有静默吞掉远端认证/服务错误。
- Python 测试对 LLM JSON 解析、平台分支、mygene 返回结构等确定性行为覆盖较广；本机实跑 141 项全部通过。
- 数据与结果文件的 Git ignore 当前有效：本地 h5ad、`data/_subset/`、`.env`、缓存均未被 Git 跟踪。
- Python、R、Shell 和 YAML 至少通过了语法级检查；脚本普遍有用途说明和中文解释。

## Critical / 必改

### C1. SoupX 丢弃空液滴后再估计 ambient RNA，方法输入已失真

- **位置**：`scripts/soupx_run.R:92-114`、`scripts/soupx_run.R:152-154`
- **问题**：代码先求 filtered 与 raw barcode 的交集，再把 `raw_counts` 也裁成 `matched_bc`。这样传给 `SoupChannel(raw_counts, filtered_counts)` 的所谓 raw 矩阵只剩已过滤细胞，空液滴/背景 droplets 被全部删除。SoupX 估计 soup profile 的关键信息正来自 raw droplet pool；当前实现实质上破坏了算法前提。
- **影响**：ambient RNA 污染比例及校正 counts 可能系统性错误，且下游聚类、marker、差异表达都会继承该偏差。这不是性能或风格问题，而是会改变生物学结论的实现错误。
- **具体改法**：核心 SoupX 代码与参数移回调用 notebook 的可见 cell。`tod` 必须保留完整 raw droplets，`toc` 只含 filtered/QC cells；仅对基因轴和 filtered barcode 的存在性做校验，不得把 raw 细胞轴裁成 filtered 集。明确打印 `n_raw_droplets`、`n_filtered_cells`、两者比例和 overlap 断言。
- **回归测试**：构造含 100 个 raw droplets、20 个 filtered cells 的小矩阵，进入 `SoupChannel` 前断言 raw 仍为 100 列、filtered 为 20 列；加入一个仅在空液滴中高表达的 ambient gene，验证校正后该基因在细胞中的 counts 下降。

### C2. SoupX 失败时把未校正 counts 写成 `corrected_counts.mtx`

- **位置**：`scripts/soupx_run.R:163-193`、`scripts/soupx_run.R:207-234`
- **问题**：`autoEstCont` 三次失败后返回 `NULL`，代码却将原始 `filtered_counts` 赋给 `corrected`；`adjustCounts` 失败也同样回退原矩阵。随后仍写入名为 `corrected_counts.mtx` 的正式产物，没有机器可读的失败状态，也不以非零退出码中止。
- **影响**：notebook 和后续 stage 无法区分“成功校正”与“完全未校正”。日志中的 warning 很容易被忽略，结果文件名会制造错误信心，属于科研结果不可伪造原则下的 Critical 问题。
- **具体改法**：失败必须二选一：默认 `stop()` 非零退出；或由 notebook 中显式的 `ALLOW_UNCORRECTED_FALLBACK=False` 开关决定是否保留未校正矩阵。若人为允许 fallback，输出文件必须命名为 `uncorrected_counts.mtx`，同时写 `soupx_status.json`，记录 `status/method/parameters/error/rho`，notebook 显著显示红色警告并要求人工确认。
- **回归测试**：mock/小夹具令 `autoEstCont` 与 `adjustCounts` 分别失败，断言默认退出非零、不得生成 `corrected_counts.mtx`；显式允许 fallback 时断言状态文件为 `uncorrected_fallback`。

### C3. DESeq2 把 count matrix 转成无维度 integer vector

- **位置**：`scripts/deseq2_contrast.R:69-87`，尤其 `:80`
- **问题**：`as.integer(round(counts))` 在 R 中会丢失 matrix 的 `dim` 属性，返回一维 integer vector，却被传给 `DESeqDataSetFromMatrix()`。本机直接验证：`as.integer(round(matrix(...)))` 的 `is.matrix()` 为 `FALSE`。
- **影响**：真实 pseudobulk 分析会在 DESeq2 构造阶段失败；当前 CI 完全不执行该脚本，因此 141 个绿色测试没有覆盖这一主路径。
- **具体改法**：分析代码移回 notebook 可见 cell。保留矩阵结构，例如 `counts_int <- round(counts); storage.mode(counts_int) <- "integer"`，并在调用前断言 `is.matrix(counts_int)`、`ncol(counts_int)==nrow(metadata)`、列名与 metadata 行名同序、counts 非负有限。
- **回归测试**：使用 20 genes × 6 pseudobulk samples 的小型真实 DESeq2 fixture 跑完整入口，断言返回表行数、contrast 方向和已知上调基因符号；加入列名错位、非整数、每组样本不足的失败用例。

### C4. notebook 冒烟脚本可以在管线失败时仍返回成功

- **位置**：`scripts/smoke_run_notebooks.py:115-131`、`:143-180`、`:185-205`、`:239-256`
- **问题**：脚本使用 `--allow-errors`；状态判定不把 subprocess `returncode` 和 `output_exists=False` 纳入失败；注释称“core failed 则 skip downstream”，实际无条件执行全部 downstream；`main()` 最终不根据结果 `sys.exit(1)`。此外，无输出的正常赋值 cell 被标成 `SKIP`，不能代表“未执行”。
- **影响**：自动化或人工看到命令退出码 0、`PIPELINE TEST COMPLETE` 时，无法确认主线是否成功、正式输出是否新生成，属于典型假绿。旧结果文件存在时还可能把本轮未产出的结果误判为存在。
- **具体改法**：运行前记录/清理目标产物或校验 mtime/run-id；任何 cell error、非零 returncode、必需输出缺失/为空都令 stage `FAIL`；核心 stage 失败后 downstream 标为 `BLOCKED` 而非继续；最终存在任一 `FAIL/MISSING/TIMEOUT/BLOCKED` 时退出非零。用 execution count 判断 cell 是否执行，不以 outputs 为空判断。
- **回归测试**：用 4 个微型 notebook fixture 分别模拟成功、cell 抛错、无输出赋值 cell、未写预期文件；测试最终状态和进程退出码。再测 core 失败后 downstream 的执行函数未被调用。

## Important / 应改

### I1. `src/io.py` 越过项目已定稿的 src/notebook 边界

- **位置**：`src/scrna_integration/io.py:25-179`、`:187-307`、`:315-353`；`src/scrna_integration/__init__.py:9-10`
- **问题**：项目铁律只允许 src 保留 LLM、平台检测、启动脚手架、RDS 跨语言读取四类技术管道；但 `io.py` 包含 gene symbol/Ensembl 选择、mygene 映射策略、多位点取第一个、CNV 位置信息注入、batch 语义诊断。这些都会影响保留哪些基因、如何解释基因组位置和批次，属于需要专家看见和调试的分析决策，不是无科研价值的 IO。
- **影响**：生物医学使用者只能调用黑箱函数，无法在 notebook 中方便查看命中率、歧义映射、版本后缀、重复 symbol、染色体筛选和失败基因清单。当前 `sync_gene_ids()` 对 0 gene 输入还会直接 `IndexError`（`io.py:37`），错误不可诊断。
- **具体改法**：从 `src` 移除上述分析函数及顶层 re-export。把每个 stage 实际需要的映射代码写回 notebook，集中放在“参数区 + 映射诊断 + 人工确认”连续 cells 中；至少暴露 `species/scopes/batch_size/ambiguity_policy/duplicate_policy/allowed_chromosomes/min_mapping_rate`。若保留跨语言读取 helper，只做 RDS→中间格式读取，不做字段/基因语义判断。
- **回归测试**：notebook 静态测试禁止 `from scrna_integration.io import sync_gene_ids/inject_genomic_positions`；对空基因、混合 ID、版本后缀、重复 symbol、多 genomic hits、低映射率分别建立可见诊断用例。

### I2. R 分析脚本把关键参数与回退策略藏在 notebook 外

- **位置**：`scripts/deseq2_contrast.R:58-103`；`scripts/soupx_run.R:115-213`
- **问题**：DESeq2 design、contrast、显著性阈值；SoupX HVG 数、PCA rank、kNN、聚类算法、`tfidfMin`、`soupQuantile`、`priorRho`、`forceAccept` 等核心参数都在脚本内部硬编码。用户从 notebook 只能传少量位置参数，无法逐步调试中间对象。
- **影响**：直接违背“notebook 对生物医学专家友好、参数充分暴露”的目标。尤其 SoupX 第三次回退使用 `priorRho=0.05` 和 `forceAccept=TRUE`，这是实质科研假设，不能隐藏为技术容错。
- **具体改法**：把 R 分析通过 `%%R`/rpy2 或 notebook 生成的、完整展示的 R cell 执行；参数统一置于 notebook 顶部 PARAMS 区并逐项注释 Why。脚本若必须保留，只能是无判断的跨语言传输/启动 wrapper，参数与分析主体仍需在 notebook 显示。
- **回归测试**：静态检查 scripts 中不得出现 `DESeq(`、`autoEstCont(`、`adjustCounts(` 等分析调用；notebook 参数契约测试确认所有关键参数存在且打印实际值。

### I3. obs 对齐的 prompt 与 manifest 合并规则也被隐藏在 `.py` helper

- **位置**：`notebooks/_llm_proposer.py:31-169`、`:264-337`
- **问题**：允许 LLM 提议哪些规范字段、如何展示 obs/临床信息、ontology 提示、冲突时“不覆盖”规则，都决定字段映射与数据语义，却封装在 notebook 外。文件名位于 `notebooks/` 并不等于 notebook 可见。
- **影响**：PI 无法在运行页面直接修改字段白名单、疾病系统提示、映射冲突政策或逐条审查合并逻辑；也难以理解为何某项 proposal 被保留/忽略。
- **具体改法**：将 prompt 模板、字段白名单、proposal 展示表、确认开关和 merge policy 放回 `00_propose_obs_manifest.ipynb`。只允许把纯 JSON/YAML 解析、原子写文件等无科研判断代码保留为极薄 helper；写入前显示 diff，并要求显式 `CONFIRM_WRITE=True`。
- **回归测试**：构造冲突 mapping，验证 notebook 显示 old/proposed/final 三列；未显式确认时 manifest 不得变化；非法字段和 ontology term 必须进入待人工处理列表而不是静默丢弃。

### I4. bootstrap 的线程限制在 NumPy 导入后才执行，且打印值可能与实际环境不一致

- **位置**：`src/scrna_integration/__init__.py:9-17`、`src/scrna_integration/io.py:16-17`、`src/scrna_integration/bootstrap.py:58-69`、`:85-86`
- **问题**：执行 `from scrna_integration.bootstrap import init` 时，Python 会先执行包 `__init__.py`，其 eager import `io.py`，继而导入 NumPy/Pandas；之后 `init()` 才设置 BLAS 环境变量，可能已错过底层线程池初始化。本机验证：导入 bootstrap 后 `numpy in sys.modules == True`。同时 `setdefault()` 保留用户已有值，但 verbose 总是打印字典里的 `4`，不是 `os.environ` 的真实值。
- **影响**：服务器线程爆炸风险仍可能存在，且 notebook 诊断会错误显示“限制为 4”，降低调试可信度。当前 bootstrap 覆盖率为 0%。
- **具体改法**：令 `__init__.py` 保持最小且不 eager import 科学栈；bootstrap 必须在任何 NumPy/torch/scanpy 导入前运行。打印每个变量的实际值和来源（default/user-existing），并检测 NumPy 已加载时发出显著 warning。更稳妥的是由 kernel 启动环境设置线程变量，notebook 只诊断。
- **回归测试**：新 Python 子进程中导入 bootstrap，断言 NumPy 尚未加载；预置 `OMP_NUM_THREADS=12` 后断言输出显示 12 而非 4；NumPy 先导入时断言出现“设置可能过晚”警告。

### I5. LLM 多 group 配置会覆盖同 provider 的不同端点，Anthropic temperature 参数无效

- **位置**：`src/scrna_integration/llm_config.py:421-461`、`:299-312`
- **问题**：`api_keys`/`base_urls` 以 provider 名为 key；两个独立 group 若都为 `anthropic` 或同一 OpenAI-compatible provider，后一个会覆盖前一个，但 `model_list` 保留全部模型，导致模型可能被错误路由到最后一个端点。另一个用户可调参数 `temperature` 只传给 OpenAI 分支，Anthropic body 未包含该字段，用户调参对 Anthropic 不生效。
- **影响**：多模型共识可能没有按配置的独立端点运行；annotation 的可重复性和参数解释出现偏差。
- **具体改法**：配置结构以 group id 为主键，显式保存 `{group, provider, model, key, endpoint}`，不要降维成 provider→credential；调用结果记录实际 group/model/endpoint（脱敏）和 temperature。Anthropic 分支显式传 temperature，或在 notebook 中明确标为该 provider 不支持且禁用控件。
- **回归测试**：两个同 provider、不同 endpoint/key 的 group，断言各模型调用对应端点；Anthropic 请求体断言含用户设置的 temperature。

### I6. mLLMCelltype monkey-patch 与锁定版本矛盾，测试只验证模拟模块

- **位置**：`environment.yml:140`、`src/scrna_integration/llm_config.py:464-557`、`tests/test_llm_config.py:600-778`
- **问题**：环境锁定 `mllmcelltype==2.0.5`，patch 失败提示却声称验证版本是 2.1.1。patch 直接改第三方私有函数、`__defaults__` 和 provider registry，强依赖内部签名；测试构造假的模块树，不能证明锁定的真实 2.0.5/2.1.1 可用。
- **影响**：真实 notebook 可能在库升级/降级后静默返回 `False` 并跳过 LLM 注释，而 CI 仍全绿。
- **具体改法**：先统一唯一验证版本；增加真实包契约测试，检查签名、patch 后的一次本地 fake-HTTP 调用和解析。更稳妥的是避免 monkey-patch 私有 API，优先用项目自己的统一 LLM caller，或将补丁限制为版本严格匹配，不匹配直接阻断该可选步骤并显示升级说明。
- **回归测试**：在隔离环境安装 exact pinned mllmcelltype，运行 patch+本地 HTTP stub；版本不匹配时必须给出明确 `unsupported_version`，不得只泛化为“跳过”。

### I7. CI 的 `lint` required check 是固定假绿，R/脚本/notebook 路径均未形成门禁

- **位置**：`.github/workflows/lint.yml:22-38`、`.github/workflows/test.yml:24-64`
- **问题**：ruff 和 R lintr 后均有 `|| true`；本机 `ruff check src tests scripts notebooks/_llm_proposer.py` 实际返回 52 个错误，但 CI lint 仍成功。R workflow 仅在存在 `DESCRIPTION` 时运行，而本项目没有，因此 3 个 R 脚本从不被 CI 解析/执行。test workflow 也不运行 shell syntax、R script integration、notebook 静态契约或冒烟 runner。
- **影响**：`_project.md` 把 `lint` 列为 required check，但这个 check 无阻断力。DESeq2 的 Critical bug正是在该空白中长期存活。
- **具体改法**：移除 `|| true`；ruff 范围明确为正式 Python 代码并清零现有错误。单独增加 `Rscript parse`、`bash -n`、notebook 静态检查 job；为 DESeq2/SoupX 建最小 integration job。不要依赖 `DESCRIPTION` 判断本仓是否有 R 代码，改用 `hashFiles('scripts/**/*.R')`。
- **回归测试**：在 CI fixture 中故意加入 Python undefined name、R syntax error、Shell syntax error，确认对应 job 失败；required checks 与真实 job 名一致。

### I8. 覆盖率总阈值掩盖关键模块 0% 覆盖，LLM 路径可因缺依赖整体 skip

- **位置**：`pyproject.toml:116-119`、`tests/test_llm_config.py:385-389`；本次 coverage 报告 `bootstrap.py 0%`
- **问题**：只设置全包 70% 总阈值，因此 bootstrap 0% 仍由其他文件覆盖率抵消。LLM caller 测试在 requests/openai 任一缺失时整类 skip，而 CI 的 `.[dev]` 不包含 annotation extra，openai 很可能缺失。`tests/test_smoke.py` 也只验证 import，不是管线 smoke test。
- **影响**：最关键的启动、真实 LLM、R 和 notebook 路径没有保护，但“84% coverage”容易被误读为整体充分。
- **具体改法**：为每个正式模块设最低覆盖或至少 bootstrap 关键分支强制测试；CI 显式安装测试所需依赖，不允许核心测试 skip；`pytest -ra` 后检查 unexpected skips。把 import test 重命名，避免与真实 smoke 混淆。
- **回归测试**：CI 断言 skip 数为预期白名单；bootstrap 单独达到关键分支全覆盖；真实依赖版本契约测试作为独立 job。

### I9. 环境规范与快照已明显漂移，诊断工具比较大量平台噪声却不核验直接依赖

- **位置**：`pyproject.toml:28-95`、`environment.yml:30-279`、`scripts/env_parity.py:153-220`、`:230-317`
- **问题**：pyproject 使用宽泛 `>=`，CI `pip install -e .[dev]` 会安装当日最新版本，而科研环境使用精确 pin；两者不是同一被测系统。本次 `env_parity.py compare` 返回 314 项差异，快照中 Mac 主环境仍有 TensorFlow/Keras，且 Python/R 版本也与当前 spec 不同。compare 把大量预期的平台工具链差异与真正关键的直接依赖漂移混在一起，未读取 exceptions 或 direct-dependency allowlist。
- **影响**：CI 绿不能证明精确科研环境可运行；parity 报告噪声过大，生物医学用户难以判断哪些差异会改变结果。
- **具体改法**：CI 至少增加从 `environment.yml`/lock 创建的代表性 job；pyproject 若保留开发安装，应使用 constraints 与科研 spec 对齐。parity 分成三层：直接分析依赖（必须一致）、批准的平台例外、传递/工具链信息；关键版本漂移单独非零退出。快照更新前先通过脱敏与环境冲突检查。
- **回归测试**：人为改变 scanpy/anndata/numpy/scvi-tools 版本时 compare 必须明确失败；仅平台工具链差异时归入 exception，不淹没关键结果。

### I10. fixture 生成器不可移植、失败仍退出 0，且清单声称用途与实际测试脱节

- **位置**：`scripts/make_test_subset.py:47-56`、`:358-402`、`:555-606`；`scripts/README.md:17`
- **问题**：所有源数据路径硬编码为单台 Mac 的 `/Users/...`；Tsubosaka 仍为 TODO；其他来源失败仅打印，`main()` 不返回非零。README 声称夹具供 pytest 和 CI 使用，但当前测试不读取这些 fixture，CI 也不生成/验证它们。
- **影响**：换机器或交给学生时脚本无法直接复用；自动化无法从退出码判断夹具是否完整，所谓“真实集成夹具”没有形成测试保护。
- **具体改法**：源路径改为 CLI 参数/本地不入库配置，并在启动时打印解析结果；定义 `--required-sources`，任何必需来源失败即退出非零。完成或明确移除 Tsubosaka 承诺；加入 fixture manifest（hash、shape、obs/var 契约、抽样 seed），pytest 对实际小夹具做最小读取契约验证。
- **回归测试**：临时目录模拟缺路径/部分文件，断言退出码；相同 seed 重建两次比较细胞 ID 与 hash；fixture schema 变化时测试失败。

### I11. CUDA 安装脚本在 CUDA/cuDNN 不可用时仍打印 Done 并退出 0

- **位置**：`scripts/setup_cuda.sh:16-55`
- **问题**：验证 Python 只打印 warning，不在 `torch.cuda.is_available()==False` 或 cuDNN 不可用时 `sys.exit(1)`；脚本随后无条件输出 `=== Done ===`。同时 `--no-deps` 跳过 CUDA runtime 依赖，把成功建立在机器外部库恰好完整的假设上。
- **影响**：学生可能认为 GPU 已配置成功，实际训练走 CPU 或运行期失败，造成数小时级资源浪费和结果环境记录错误。
- **具体改法**：增加 `--allow-system-cuda` 显式模式；默认安装完整 wheel 依赖或验证系统库。CUDA/cuDNN/版本不满足时退出非零；成功时写出脱敏的设备诊断 JSON，notebook `env_check()` 读取并显示。
- **回归测试**：mock `torch.cuda.is_available=False`、cuDNN false、版本不符三种场景，断言非零；成功场景断言报告包含 torch/cuda/cudnn/GPU 型号。

### I12. 依赖追踪脚本会漏报并给出“可安全修改”的过强结论

- **位置**：`scripts/trace_downstream.py:24-36`、`:39-73`、`:100-104`
- **问题**：脚本只用正则识别字面量 `UPSTREAM_PATH="..."`/`OUTPUT_PATH="..."`，无法识别 `Path(...)`、变量拼接、列表输入或其他读文件方式；按 basename 匹配还会把不同目录同名文件混为一谈。即便零匹配，仍输出“可安全修改不影响其他 stage”。
- **影响**：PI 可能依据不完整静态扫描少重跑下游，产生旧结果与新上游混用。
- **具体改法**：把结论降级为“未检测到声明式依赖，不代表无依赖”；优先让 notebook 参数 cell 输出机器可读 dependency manifest，再按规范化绝对/项目相对路径构图。检测到动态路径时列为 `UNKNOWN`，不能判 safe。
- **回归测试**：覆盖 Path、变量拼接、列表、多目录同名文件、动态路径；UNKNOWN 时退出码/报告必须提示需人工核查。

### I13. 公共环境快照写入 hostname/内核信息，违反公开仓脱敏纪律

- **位置**：`scripts/env_parity.py:158-205`、`docs/env-snapshots/linux-64.json:2-9`、`docs/env-snapshots/osx-arm64.json:2-9`
- **问题**：snapshot 主动采集并建议提交 hostname、完整 kernel release、完整 Python build 字符串；当前公开快照已包含具体机器名。项目级规则明确要求公开仓状态与产物避免真实内部环境细节。
- **影响**：造成不必要的基础设施指纹暴露；每次刷新都会继续传播。
- **具体改法**：快照只保留匿名 platform tag、必要版本和 GPU capability；移除 hostname、generated_by 机器名、完整内核 patch/build 信息。对既有 Git 历史是否清理由 PI 单独决策，本次不擅自改历史。
- **回归测试**：快照 schema 测试禁止 `hostname`，并对 `/Users/`、`/home/`、内网地址、用户名模式做脱敏扫描。
