# 生产整改决策与 Notebook UX 规格（01–06）

> 本文件把 2026-07-14 PI 与主 Agent 的整改讨论逐条固化为可执行规格。此前 `docs/manifest-schema-migration.md` 把 counts 来源 / SoupX 使用范围 / 数据尺度语义显式排除出 schema 迁移序列（"定义在别处"），但仓内无承接文档——本文件补上这一缺口。
>
> **性质**：这些是 PI 的科研判断，不是 agent 可自行捏造的工程默认。每条决策均已 PI 明确拍板（原始对话记录为准）。执行时任何偏离须回到 PI。
>
> **边界**：本轮只解锁 01–06 主线。GRN、CellChat、trajectory-DE、D02 pseudobulk DEG 暂缓，不计入 01–06 解锁条件。

## 零、共识总览（PI 定稿）

1. 四来源均已找到真实 counts；`layers["counts"]` 是唯一权威原始计数层。
2. SoupX 独立处理，仅支持兼容的 QC、doublet、marker/DEG 等用途，**不进入 scVI/scANVI**。
3. 默认输出为**排除高置信 doublet 后的高质量细胞**。
4. scVI/scANVI 严格读取原始 counts，非法输入不降级、不静默 fallback。
5. fresh-kernel、真实参数消费、失败不写正式 checkpoint 是硬门槛。
6. LLM 只生成 suggested；final 必须经过完整、显式、可追溯的 PI 确认。
7. 上游数据视为已脱敏，不增加逐次外发审核；但须修复 LLM 路由并保留复现信息。
8. 研究者自主勾选整合方法、候选 resolutions，并据充分展示的证据选择结果。
9. Notebook 采用 guided workflow、独立 RUN_ID、显式状态机、可验证 checkpoint。
10. 轻量运行证据长期保留，大型产物只由研究者显式清理。

## 一、决策 1 — raw counts 与数据尺度契约（双轨制度）

**问题（已证实）**：当前代码把不同意义的数据当同一种用。Nowicki 的 `X` 已归一化，其他来源 `X` 是 raw counts；02 直接拼接；任一来源标记做过 normalization 就可能令 03 对整个合并对象跳过归一化；随后又可能把混合尺度 `X` 写成 counts layer。后果：HVG/PCA/聚类/批次校正失真、scVI 输入不成立、结果能跑但无法科学解释（比报错更危险，列 Critical）。

**PI 拍板**：接受双轨制度。
- raw counts 是进入**正式整合分析**的准入条件。
- normalized-only 来源只能作探索性数据，直到找回 raw counts。

**后续盘点结论（PI 追加，已确认）**：四来源均已找到真实 counts，无需降级为探索性：
- Nowicki：manifest 使用的 2500-cell h5ad，`X` 是 logcounts，`.raw.X` 是全量非负整数 counts，与当前细胞/基因完全对齐。
- Kim：`X` 为真实整数 counts。
- Nancang：10x/旧链 `X` 及 `layers["counts"]` 均有合格 counts。
- Yue：29 个输入文件均存在 counts。
- **保留限制**：Nowicki 完整原始文件当前不在本机，现阶段验证针对 manifest 实际使用的子集文件。
- 证据：`代码审查-20260713/h5ad-counts盘点.md`。

## 二、决策 2 — 01–03 表达矩阵契约

| 位置 | 固定语义 |
|---|---|
| `layers["counts"]` | 与当前细胞/基因对齐、经验证的分析用 counts；01 起建立，之后**不得被 normalization 覆盖** |
| `X`（01、02） | counts 工作矩阵，便于 QC、拼接、预处理 |
| `X`（03 以后） | 统一生成的 normalized/log1p 表达矩阵 |
| `.raw` | 只作输入来源或历史快照，**不再作为下游 counts 的权威位置** |
| `uns["expression_contract"]` | 记录 `X` 当前尺度、counts 来源、验证状态、处理历史 |

**执行**：
1. 01 对每个来源寻找真实 counts（Nowicki 从 `.raw.X` 提取，其他从已验证位置），统一写入 `layers["counts"]` 并记录来源与验证结果。
2. 02 拼接前逐来源检查契约，任一不合格即停止——**不靠全局 `preprocessing_done` 猜状态**。
3. 03 只从 `layers["counts"]` 生成统一 normalized `X`；完成后验证 `layers["counts"]` 未变，禁止把 normalized `X` 回写成 counts。
4. 下游只按显式契约选矩阵，不靠 `.raw` 是否存在或数值像整数来猜。

**代价**：01/02 中 `X` 与 `layers["counts"]` 有数据重复，增加磁盘占用；PI 认定科研可信性优先于此存储成本。

**PI 拍板**：同意。`.raw` 仅作输入来源，`layers["counts"]` 是进入框架后唯一 counts 权威位置。

## 三、决策 3 — SoupX 进入正式流程（有能力才启用、启用即严格成功）

**问题（已证实）**：SoupX 需 `tod`（完整 raw droplet matrix，含空液滴，估计环境 RNA）与 `toc`（过滤后细胞矩阵）。当前 R 脚本先取 barcode 交集，把两者都裁成 filtered cells → 空液滴全丢，环境 RNA 估计基础被破坏。另两个确定问题：① 估计/校正失败时脚本仍把原矩阵写成 `corrected_counts.mtx` 并以成功状态退出；② Python 覆盖 `X` 后未重算 `total_counts`/`n_genes`/线粒体比例等 QC，后续过滤用的是校正前指标。

**PI 拍板**：
- 只有**同时具备完整 raw droplets 和 filtered cells** 的来源才允许启用（目前仅 Nancang）。
- `tod` 保留完整 droplet barcode，`toc` 保留 filtered cell barcode，**只对齐基因，不对齐后裁空液滴**。
- 原始 filtered counts 始终存 `layers["counts"]`，**不允许覆盖**；SoupX 成功结果单独写 `layers["counts_soupx"]`，记录参数、污染率、状态。
- SoupX 校正后**重算全部 QC**，再做正式 QC 过滤与 doublet 检测。
- 启用但失败 → **该样本直接失败**，不得把未校正矩阵冒充成功。
- PI 可显式关闭 SoupX，以未校正 `layers["counts"]` 继续（属明确选择，非 fallback）。
- 增加含空液滴/真实细胞/环境基因的最小集成测试，再用 Nancang 做校正前后回归比较。
- 未量化项：代码路径错误已证实；对 Nancang 污染率/聚类/marker 的具体偏差量待正式重跑量化。

## 四、决策 4 — scVI/scANVI 输入与失败语义

**问题（已证实）**：04 校验结果没真正控制训练输入——只抽查前 500×500，发现 counts 非整数则查 `.raw.X`，但即使 `.raw.X` 合格也不覆盖坏 counts，训练键仍设 `"counts"`，模型仍读有问题的 counts；所有候选都不可用时又静默跳过 scVI 继续 PCA/Harmony，使产物看似完整成功。

**PI 拍板**：
1. scVI/scANVI **默认只读 `layers["counts"]`**（负二项模型针对未归一化计数）；进入 04 后不再从 `.raw` 临时补救，`.raw`→counts 提取必须在 01 完成。
2. 训练前严格校验：shape 与 obs/var 一致、gene 顺序未漂移、全部值有限非负、全量或分块检查近整数性、每批次每来源有有效文库大小、契约元数据确认来源与处理历史（稀疏矩阵可分块检查）。
3. 非法输入**必须阻断所选方法**：配置用 scVI/scANVI 时输入不合格即该方法失败；不静默改用 `.raw`；不静默改用 PCA/Harmony；若预配置主方法是 Harmony，则 scVI 未运行不算失败；比较多方法时每种分别记录 success/failed/not_requested，不能用一个结果冒充全阶段成功。
4. `counts_soupx` 暂不作为 scVI 默认输入（只有 Nancang 具备，单来源用校正 counts 会引入来源特异预处理差异；取整后也非直接观测计数）。默认 scVI 用四来源统一原始 `layers["counts"]`；`counts_soupx` 用于 Nancang 污染评估/QC/敏感性分析；将来若要用 `counts_soupx` 喂 scVI，作单独 A/B 实验，不进首轮正式基线。

**PI 追加**：若 SoupX 的 count 输出不适合 scVI/scANVI，则该部分独立处理——只在 DEG 或其他能用的地方采用。

**DEG 使用边界（主 Agent 补充约束，PI 认可）**：`counts_soupx` 也不是所有 DEG 都能直接用，看统计方法输入要求。
- 可用：Nancang 污染评估、校正后 QC、支持相应输入的 doublet 方法、校正后归一化的 marker/可视化。
- Nancang 单来源 DEG：可用，但 DESeq2 等要求整数时须明确 SoupX 整数化策略，并同时保留原 counts 敏感性分析。
- 跨来源正式 DEG：主分析统一用原始 counts；不能只校正 Nancang、其余不校正后混合；可把"替换 Nancang 为 counts_soupx"作为敏感性分析。
- 不使用：scVI/scANVI，及任何未明确声明兼容 SoupX 输出的方法。

## 五、决策 5 — Notebook 在 fresh kernel 下真实可复现（硬门槛）

**问题（已证实的确定性 bug）**：
- 04 循环生成 `_m` 却调用 `m.items()`：嵌入列表非空则首次运行必 NameError。
- 05 相同 `_m/m` 错误：分辨率列表非空则聚类 sweep 首轮必崩。
- 06b 在定义 `OUTPUT_VERSION` 前就用它构造路径：fresh kernel 必崩，旧 kernel 残留变量反而掩盖错误并读错版本。
- 参数看似可改实际没进模型：`SCVI_GENE_LIKELIHOOD` 被硬编码 zinb 覆盖、`SCVI_EARLY_STOPPING` 实际固定 True、`SCANVI_N_EPOCHS` 未生效、`SCANVI_LABEL_KEY` 被自动搜索替代、04/05 用 `'results' in dir()` 判断结果可能消费旧 kernel 残留。
- 报告能证明确定性错误存在，但不能证明哪些历史结果已被旧状态污染。

**PI 拍板**：把 fresh-kernel 全链执行 + 参数真实消费设为 01–06 解除 BLOCK 的硬条件，不是只修三个报错。具体：
1. 修现有 NameError 和版本定义顺序。
2. CI 对 01–06 用最小数据做真正的 Restart Kernel + Run All。
3. 禁止用 `dir()` 或变量残留决定流程；每轮显式初始化状态。
4. 所有公开 PARAMS 必须真实传入对应方法，并把 effective parameters 写入产物。
5. 加"参数消费测试"：改参数后实际调用参数及输出元数据必须同步改变。
6. 拆分 06b 300+ 行巨型 cell（至少：输入检查/参数/执行/QC/保存）。
7. 必需步骤失败时不写正式 checkpoint；临时结果用独立路径和失败状态。

## 六、决策 6 — 版本契约与 PI-final 闸门

**问题（已证实）**：
- 版本混用：06 输出路径写死 v1 但标签列/元数据按 `OUTPUT_VERSION` 动态生成；06c 用一个 `OUTPUT_VERSION` 同时操作上游粗标签/subset 结果/主对象回流；部分路径写死 v1、主输出写死 v2；06b 先用后定义版本变量。可能一个名为 v2 的文件读 v1 标签、元数据又声明另一版本、甚至回流到错误主对象。
- PI-final 绕过：LLM 高置信标签自动预填 PI 决策；任一标签非空就可能创建 `cell_type_final_*`；未填簇由 `Cluster_N` 自动补齐；无 `PI_CONFIRMED`、无全簇覆盖检查、无确认文件 hash；部分确认/纯 LLM/占位都能写成正式 checkpoint；元数据还固定声称"PI manual review"。这是事实性错误。

**PI 拍板**：
- 版本改为独立字段：`UPSTREAM_LABEL_VERSION` / `ANNOTATION_OUTPUT_VERSION` / `SUBSET_OUTPUT_VERSION` / `MAIN_OUTPUT_VERSION`。所有路径/列名/元数据由同一份解析后配置生成，执行前检查输入版本真实存在且一致。
- 机器结果（LLM、marker 规则、`Cluster_N`）永远止于 `suggested`，绝不直接写 `final`。
- 未确认时可存 draft h5ad + 状态报告，但不生成 promoted/final checkpoint。
- PI 确认文件必须覆盖全部 cluster，至少含：cluster ID / suggested label / PI final label / accept|modify|unresolved / 备注或依据 / 当前 annotation version。
- 只有同时满足才允许生成 final：`PI_CONFIRMED=True` + 所有 cluster 有明确决定 + 无 unresolved + 确认文件版本与当前输入一致。
- final 元数据记录确认文件 hash、确认时间、标签版本；后续修改生成新版本。
- 支持"全部接受建议"批量操作，但须一次显式确认并形成逐簇审计记录。
- `Cluster_N` 只表示 unresolved 占位，不算有效细胞类型标签。
- 06c 的 subset 注释和回流主对象也须分别经过相同闸门。
- **GREEN 不默认自动转 final**：GREEN 只代表机器建议置信度高，不代表 PI 已判断其生物学合理性。

## 七、决策 7 — 外部 LLM 数据边界

**问题（已证实）**：00 notebook 把 obs 每列名/类型 + 每列前 5 个真实非空值 + 临床表每列前 3 个真实值 + 完整 manifest + 本体节点直接放进外部 LLM prompt，无敏感字段扫描/脱敏/聚合/外发确认，并打印部分 prompt/回复（保存 notebook 时可能随 cell output 留仓库）。06 风险较低（簇级信息），但涉及未发表研究数据。另有路由 bug：多个配置组用同一 provider 时，后组可能覆盖前组的 API key 和 endpoint。

**PI 拍板**：**不做严格外发限制**——进入的数据本来就是脱敏的，不必再逐次审核。
- 保留必须修复的工程项：**LLM 路由 bug** 改用唯一 `LLM_GROUP` 作路由键（非 provider 名），每次调用记录实际 group/provider/base URL/模型；保留复现信息；配置版本与环境 pin 一致；加不含真实数据的远端契约测试。

## 八、决策 8 — doublet 处理政策

**问题**：01 只算 doublet score 和预测标签，未规定是否排除、全局还是每样本阈值、异常是否阻断、排除前后如何审计。

**PI 拍板**：
- 按 sample 独立检测（不用跨来源统一阈值）。
- Nancang 在 SoupX 校正并重算 QC 后检测；其他来源用各自验证后的 counts。doublet 结果只决定细胞纳入，不改变 scVI 用原始 counts 的契约。
- **正式主分析默认排除高置信 doublet**；01 保存完整对象不物理丢失，至少记录 `doublet_score` / `doublet_prediction` / `doublet_threshold` / `doublet_include` / 方法与版本。
- 02 根据 `doublet_include` 构建正式整合对象；被排除细胞仍留在 01 checkpoint。
- 边界细胞只标记不自动排除：采用 singlet / uncertain / doublet 三态，仅高置信 doublet 默认排除。
- 每样本输出诊断（score 分布/阈值/预测比例/排除前后细胞数与 QC 差异）；预测比例异常/样本太小/无法稳定定阈值 → 进入 `needs_review`，不静默继续。
- **PI 明确：敏感性检查不必要**；默认排除双细胞后，将高质量数据输入下一步。

## 九、决策 9 — Stage 成功与正式产物契约（状态机）

每次运行先写临时目录，完成 hard postconditions 后**原子提升**为正式 checkpoint。

| Stage | 正式成功最低条件 |
|---|---|
| 01 | 所有 manifest required 样本完成 counts 校验/QC/doublet；启用 SoupX 的样本必须成功；正式输出仅含排除 doublet 后高质量细胞，完整对象另作审计产物 |
| 02 | 所有 required 来源均来自合格 01 checkpoint；cell ID 唯一、来源可追溯、counts 语义统一；不允许缺来源后静默合并 |
| 03 | `X` 从 `layers["counts"]` 统一生成 normalized/log1p；counts 前后不变；HVG 非空且参数可追溯 |
| 04 | 由研究者勾选的方法分别执行并记录状态；只比较实际选择的方法；研究者据比较填 `selected_embedding`；部分选中方法失败但仍有可用结果 → SUCCESS_WITH_WARNINGS，全部失败才 FAILED（见决策 UX-1，不强制 PCA/固定模式） |
| 05 | 所有声明的候选分辨率均成功；聚类列完整、指标对应正确；研究者选 `selected_cluster_key` |
| 06 | marker/DEG 等非 LLM 证据成功；机器标签仅 suggested；全簇 PI 决策完成后才生成 final |

**状态机**：
- `FAILED`：required 步骤或 hard postcondition 失败；不写正式 checkpoint。
- `NEEDS_REVIEW`：计算完成但等 04 embedding / 05 clustering / 06 annotation 决策；只写 draft。
- `SUCCESS_WITH_WARNINGS`：required 全成功但 optional 方法失败；PI 明确接受 warnings 后才提升。
- `SUCCESS`：required 与 hard postconditions 全通过；可提升正式 checkpoint。

每方法另记：`success` / `skipped_by_user` / `unavailable` / `failed`（区分"没要求运行"与"要求运行但失败"）。

**两条约束**：
1. 某 required 样本失败后不能运行中自动删掉继续；若决定排除须改 manifest、说明原因、产生新版本。
2. CI/R/notebook runner 不得用 `|| true`、`--allow-errors` 或最终强制退出 0；测试须验证产物和 hard postconditions，而非只跑完进程。

## 十、Notebook UX 规格（guided workflow）

**目标**：面向懂生物医学分析、但不深入维护 Python 工程的研究者的 guided notebook。不做复杂 GUI，不依赖隐藏状态的 widgets。用户只做三件事：改顶部参数 / 读 QC 与比较结果 / 明确选择或确认后继续。

**统一结构（01–06 同一骨架）**：
1. 本阶段要回答什么（生物学目的 / 输入输出 / 适用条件 / 本阶段不能证明什么）。
2. 唯一参数入口，四组排列：数据与版本 / 科学参数 / 计算参数 / 输出与运行标识。每个科学参数说明"含义、默认值、何时调整、调整风险"，不只写变量类型。
3. Preflight：执行前集中展示输入文件与版本 / 样本细胞基因数 / counts 契约 / required/optional 方法 / GPU·R·包状态 / 最终生效参数。
4. 准备 → 执行 → QC：每 cell 单一职责（约 20–60 行），执行后立即展示对应 QC，不到末尾统一补图。
5. 候选结果同屏比较：04 embedding 比较、05 分辨率比较、06 每 cluster 的 marker/证据/机器建议。
6. 独立决策 cell：只在此设 `selected_embedding` / `selected_cluster_key` / PI annotation decisions；自动建议不能直接改 final。
7. 状态与保存：最后明确显示 hard postconditions、方法状态、stage 状态；只有符合状态机才写 promoted checkpoint。

**RUN_ID 与反复调参**：每次运行用独立 `RUN_ID`，自动保存 输入文件 hash / effective parameters / random seed / Git 与包版本 / 方法状态 / QC 指标 / 选择结果 / 输出路径。改参数产生新 run 不覆盖旧结果；提供跨 run 比较表；选中的 run 再提升正式版本。断点续跑只允许从带完整 manifest 的已验证 checkpoint 恢复，不依赖旧 kernel 变量。

**注释怎么写**：不逐行解释 Python，重点解释——为什么做这一步 / 参数对应什么生物学判断 / 什么结果属异常 / 异常怎样影响后续结论 / 哪些结果需 PI 判断。会改变科研结论的逻辑/阈值/选择必须留 notebook 可见；src 只保留文件读取、环境检测、跨语言调用、API transport 等技术管道。

## 十一、三个 UX 默认项（PI 逐条拍板）

**UX-1 — 04 required 整合方法**：PI 定为**完全由研究者勾选**，不设固定 profile、不强制 PCA。
- 每方法一个"运行"勾选项，旁注输入要求 / 是否需 GPU / 预计耗时 / 适用场景 / 主要风险。
- 勾选写入本次 run manifest；不满足前置条件的方法禁用并显示原因。
- 被勾选方法分别执行并记录状态；只比较本次实际选择的方法；研究者据比较填 `selected_embedding`。
- 部分已选方法失败但仍有可用结果 → SUCCESS_WITH_WARNINGS，研究者决定是否接受并选成功的 embedding；全部失败才 FAILED。

**UX-2 — 05 分辨率选择**：研究者勾选/填写要比较的 resolution，Notebook 为每个候选统一展示——cluster 数与最小 cluster 大小 / 样本·donor·疾病来源构成 / 是否被单一数据集或 batch 主导 / marker 数量·特异性·可解释性 / 已知谱系 marker 是否合理分开 / 是否过度碎片化 / 低质量或 uncertain doublet 是否富集 / 不同 seed 或邻居参数下稳定性 / UMAP 并排图与关键指标表。系统只标记风险（"疑似过度聚类"/"样本特异簇"/"marker 支持不足"），不自动写最终聚类。研究者在独立决策 cell 选 `selected_cluster_key` 并可填一句理由，选择与证据摘要进 run manifest。PI 强调：要充分展示各 resolution 情况供综合决策。

**UX-3 — 调参 run 保留策略**：轻量证据永久保留，大型矩阵研究者显式清理。
- 每 `RUN_ID` 永久保留：effective parameters 与输入 hash / Git·包·随机种子 / stage·method 状态 / QC 与比较指标 / 图表 / 研究者选择及理由 / warning·错误摘要与产物清单。
- 大型 h5ad 三类：`promoted`（正式，永久）/ `pinned`（研究者认为值得比较的候选，保留）/ `superseded|failed`（不自动删，进清理清单）。
- Notebook 提供 run 管理表（状态/参数差异/选用结果/文件大小/最后访问时间）；研究者勾选后才清理大型 h5ad，清理后仍保留 manifest/指标/图表。
- 失败 run 不生成正式 checkpoint 但保留错误记录与诊断；临时未完成文件与正式产物用不同目录避免误读。
- 不按"只留最近 3 次"自动删除；磁盘压力时按 run 管理表集中清理。

## 十二、实施顺序（分 PR，PI 认可）

Notebook UX 与正确性整改进同一路线，分 PR 推进；每期同步把该阶段隐藏在 helper 中的科研逻辑迁回 notebook，不留到最后返工。
